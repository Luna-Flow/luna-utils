# Float conformance and limits

The contract separates exact integer encodings from portable numeric observations. Raw tests cover every classification, signed zero, exponent boundaries, NaN quiet bits, both signs, payload width limits and signaling-zero rejection. Rounding tests cover all five IEEE 754-2019 §5.9 directions, positive and negative ties, the predecessor of 0.5, negative zero, large integral values and infinities. Numeric tests use `x != x` for NaN and compare canonical integer output, never input NaN metadata.

Integer conversion tests are table driven. For each binary format a generated table lists the exact rounded integer of every input in each of the five directions (computed offline with `fractions.Fraction`, or marked NaN, at least `2^64` or at most `-2^64`). The test converts every input with all sixteen functions in the checked-presence, checked-value and saturating modes, in all five directions through the `_with` forms and once through the default functions, and compares each result with the table. The inputs include `+0` and `-0`, `±0.5` and the other eighths below 9, halfway and quarter points next to every power of two `2^j` for `j = 0..69`, the sweep `2^k` and its neighbors one ulp away, the neighborhoods of `±2^31`, `2^32`, `±2^63` and `2^64` with fractional parts `0`, `1/8`, `1/4`, `1/2` and `3/4`, infinities, quiet and signaling NaNs with payloads, the smallest subnormal and the largest finite values, and 64 seeded random encodings. The default functions truncate; changing the default direction of any of them to `TowardPositive` fails the test (checked by mutation). For `Int64` and `UInt64` converted to binary32 and binary64, the table covers `2^k` and its neighbors for `k = 0..63`, halfway and nearby remainders for 24-bit and 53-bit significands, `2^64 - 1`, values near `2^64 - 2^39`, and `2^53 + 2^29 + 1`, where rounding through binary64 first gives the wrong binary32 result.

Ordering tests cover both argument orders for minimum/maximum, signed-zero selection, raw totalOrder across signed qNaN/sNaN payloads, portable NaN canonicalization, and array and mutable-view sorting. The generated integer-key oracle compares all pairs in a boundary sample for both binary formats.

Four-backend debug/release checks and exact transcript comparison follow the [CI contract](../testing.md). Local results cannot establish Linux GCC behavior; CI must confirm that job. Tests are regression evidence, not a proof of all IEEE 754 behavior. No Lean/mathlib formal proof is supplied.

Exception flags, FMA, conversions, IEEE magnitude extrema, stable hashing, formatting, bigint and libm remain separate issues. Exact inexact-flag reporting for rounding waits for [issue #29](https://github.com/Luna-Flow/luna-utils/issues/29). Canonicalization is an application representation policy; it is not a promise to preserve floating-point payloads across a host round trip.

## Clause traceability

IEEE Std 754-2019 for the host binary64 (`Double`) and binary32 (`Float`) types, through `Luna-Flow/luna-utils/float` and `Luna-Flow/luna-utils/float/binary32`, which expose the same names. Status is `conforming` when the operation exists and the cited evidence exercises it, `partial` when part of the clause is missing or the evidence is thin (the cell says which), `not implemented` and `not applicable` otherwise. `Level` is `required` for clauses the standard states with "shall" and `recommended` for those it states with "should". Evidence names a test file or a tool in the repository. The roadmap that orders the gaps is [issue #50](https://github.com/Luna-Flow/luna-utils/issues/50).
